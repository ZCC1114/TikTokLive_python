# TikTok 弹幕服务架构审查

审查日期：2026-09-09。范围：`live_service/` 全部模块、相关 SDK 收包/连接代码、现有 `tests/` 和 `deploy/`。这是独立只读审查；本文不代表建议已经实施。路径和行号对应本次并行优化开始时的工作区，后续修改可能移动行号。未再次连接生产服务器，也未重新执行既有测试；“已有覆盖”指阅读到的测试代码。

## 结论

当前“每个房间一个上游连接、一个有界处理队列、每个客户端一个发送器”的结构适合这台 2 核 4 GiB 单机。继续补齐连接状态机、接入容量、去重和可观测性，比整体重写更容易得到可验证的速度提升，并降低业务兼容风险。

最优先处理：准确去重；测出并缩短重连的各阶段；为公网 WSS 增加容量与访问边界；保持 Redis 业务语义；把源代码与部署产物统一。跨进程分发、持久消息流和多机容灾应由真实并发量、允许丢失范围及可用性目标驱动，不能直接增加 Uvicorn workers。

## 按影响排序的发现

### P1：公网接入没有全局容量边界

证据：`live_service/app.py:38` 直接接受 `/ws/{live_id}`；`live_service/manager.py:111` 为每个新账号创建房间、队列和处理任务；`:237` 在取得连接信号量之前就构造 SDK。连接信号量只限制同时调用 `start()`，没有限制累计房间、订阅者、等待连接的任务或 HTTP 客户端数量。`tests/test_manager.py:248` 也表明 10 个房间在连接并发为 4 时已经构造了 10 个 SDK 客户端。

影响：偶发连接风暴、前端错误循环或任意公网调用者都可能耗尽内存、文件描述符和签名额度。每订阅者允许积压 4 MiB，并不构成进程总量上限。

建议：在创建房间/订阅者前，原子检查可配置的总房间、总订阅者、单房间订阅者上限；取得连接名额后再构造新 SDK；对账号做长度及字符校验；容量耗尽用可重试关闭码明确拒绝，避免悬挂等待。Nginx 增加握手频率和并发限制作为外层保护，注意多个合法用户共享 NAT 的场景。

验证：超过限额时不构造 SDK、不遗留任务；已有连接继续收包；释放名额后立即可接入；大量无效账号不会触发签名请求。

### P1：HTTPS 不提供调用者授权，CORS 不保护 WebSocket

证据：`live_service/app.py:30` 配置的是 HTTP CORS；`:38` 的 WebSocket 入口没有认证或 Origin 校验。当前依赖云安全组及 UFW 固定来源限制（`deploy/README.md`）。如果域名的 443 直接向全网开放，访问范围将扩大到所有知道地址的调用者。

建议：先确认该入口是固定业务服务器连接还是浏览器直接连接。固定服务器可继续使用固定出口白名单；浏览器场景可配置允许的 Origin，配合真正的调用凭证。Origin 只防浏览器跨站滥用，不是身份认证。兼容阶段不要无声更改现有 URL、消息协议或要求客户端发送新字段；至少完成总量限制，必要的认证变更单独说明接入方式。

### P1：14.9 秒只覆盖显式断线恢复，静默网络故障可能更慢

证据：`TikTokLive/client/ws/ws_connect.py:69` 使用 TCP 空闲 30 秒、间隔 10 秒、3 次探测及 60 秒 `TCP_USER_TIMEOUT`；`ws_client.py:250` 禁用标准 WebSocket ping/pong；`:334` 的应用心跳只检查写入是否成功。内核接受写入不表示对端仍可达。

影响：现有显式故障注入不能证明半开连接、网络黑洞的发现时间；无新弹幕也不能直接认定网络已断，因为直播间可能安静。

建议：分别记录“故障发生→被发现”和“被发现→再次 LIVING”。新连接分解为排队、账号解析、在线检查、签名、WS 握手、入房。优化已知可省略的重复阶段，保留签名刷新及限流退避。半开检测采用可配置的 TCP 超时和可验证的上游活动信号，不能简单用“无评论几秒”强制断线，也不要启用上游不支持的 pong 超时。

验证：RST、正常 close、对端不应答、丢弃网络流量、签名 429、短时 DNS 失败分别测量；给出样本数和 p50/p95/max，不以单次成功值保证所有外部网络场景。

### P1：源弹幕 ID 的重复目前没有在同次连接内抑制

证据：`live_service/delivery.py:47` 仅当相同 `source_key` 的 generation 不同才抑制；`manager.py:196` 先做转换和 Redis 查询才把源 ID 交给发送器；`protocol.py:33` 每次生成新的业务 UUID，所以重放消息也会得到新 `msgId`。

影响：同一上游连接重复投递同一个源事件仍会抵达客户端，并多做一次 Redis 富化。既有实测只能证明源 ID 重复，不能单凭计数确定重复来自签名历史、入房历史、帧重发或原始内容更新。

建议：在 SDK 边界记录不含正文的事件来源、源 ID、帧标识及摘要；用实际帧解析测试证明来源。按有效源 ID 和必要的内容一致性判断去重，保留不同源 ID 的相同文本、无法确认身份的消息，以及新订阅者原本可见的历史。普通弹幕重复与已修复的 ControlEvent 派生事件双处理是两个问题。

### P2：Redis 串行富化与控制状态共用队列，积压会放大反馈延迟

证据：`manager.py:165`、`:180`、`:260` 将连接/控制/错误状态放进同一个房间队列；`:197` 每条评论等待一次 Redis pipeline；`config.py:16` 允许 1024 条待处理事件。按单次读取耗时 r 估算，持续处理能力约为 1/r，尚未计入解析、序列化和分发。异步 I/O 不阻塞整个事件循环，但仍串行阻塞该房间。

建议：先记录入队时间、富化耗时、队列最老年龄与高水位；在不缓存标签、不改变先后顺序的前提下，研究有界批量 pipeline 或有限并发后按序输出。不要让 LIVING、结束状态绕过此前弹幕而造成业务乱序。必要时为传输层 pong 独立保留容量，但保持一个实际写 socket 的发送器。

现有 Redis 熔断降级方向正确。还需覆盖多房间同时在熔断到期时重试，避免同时打满连接池；配置解析失败应在启动时明确报告，不能每条弹幕重复失败。

### P2：客户端短暂掉线会触发上游冷启动

证据：`config.py:15` 的 `idle_grace=0`；`manager.py:288` 在最后一个客户端离开后立即销毁房间。`tests/test_manager.py:181` 已证明设置短宽限期能复用上游。

建议：设置短且有界的房间空闲保留期，如 2–3 秒，改善刷新页面、前端重连或瞬时网络变化。没有订阅者时不积压无意义的下行消息；宽限期结束必须释放连接。应分别报告客户端重连恢复和上游重连恢复，二者不是同一问题。

### P2：大量最终忽略的 SDK 事件仍做完整包装转换

证据：`TikTokLive/client/client.py:421` 对每条上游消息执行 `WebsocketResponseEvent().from_dict(message.to_dict())`；`:429` 解析对应事件；`:375` 调用服务 sink。服务仅使用 Connect/Control/Comment，其余返回后丢弃。

影响：点赞、入场、礼物流量高但评论量低时，仍可能消耗大量 CPU 和短期内存。连续大量不需要的事件也缺少显式协作调度点，可能增加前端 pong 与发送延迟。此项是代码路径判断，尚无该实例上的 CPU profile 证据。

建议：为服务提供可选事件订阅过滤/快速路径，只跳过业务确实不用的解析与原始包装。默认 SDK 公开监听行为保持兼容；不能删去控制事件和必要协议处理。增加大量非评论帧夹杂评论时的事件循环延迟基准。

### P2：健康指标不足以识别“进程正常但业务已经退化”

证据：`manager.py:335` 的 ready 仅表示不在关闭；`:339` 等是当前队列快照；`:344` 的抑制计数随订阅者销毁丢失；房间虽有 state/last_error/connected_at，但未公开阶段耗时。`deploy/live_probe.py:102` 每 30 秒采样，不足以证明期间从未积压。

建议：保留轻量健康检查，增加仅内部可访问的聚合质量指标：连接阶段耗时、故障发现/恢复时间、累计重连与异常原因、最新上游活动、队列年龄/高水位、Redis 延迟/降级、慢客户端关闭原因、进程累计去重。避免把账号、正文、Cookie、签名 URL 或凭证放进监控标签。

明确区分：进程存活、可接新请求、上游在线、业务标签可用。主播离线不应被误判成服务器坏了，Redis 降级也不能通过伪造默认标签掩盖。

### P2：部署文件与源代码存在人为差异，后续发布容易回退安全修复

证据：`deploy/README.md` 记录服务器 `redis_store.py` 已去除旧硬编码密码默认值，工作区 `live_service/redis_store.py:16` 仍保留旧默认。初始代码包后还有就地修改；目前仅首个完整 release。

建议：统一环境注入的配置模型，移除打包时的临时文本替换；仅打包明确列出的运行文件，不携带旧 service 配置或私钥。每次发布生成代码哈希/配置模式版本清单，安装到新 release，检查后切换 current。保留上一个完整可运行 release，而不只保留个别 `.py` 备份。迁移实际 Redis 地址及签名凭证需使用已授权的配置，不能把既有凭据自动复制到新服务器。

### P2：日志与消息积压策略需要按长期运行验证

证据：`log_config.py:13` 直接在事件循环路径使用同步文件 handler，按天轮转保留 30 份但没有总字节上限；`enrichment.py:59` 每次错误可能记一条日志；`client.py:432` 损坏 protobuf 会记录原始 payload；`delivery.py:82` 允许队列最老年龄达到 30 秒才关闭。

建议：对重复异常限频、保留累计计数；损坏帧只记录长度、类型及摘要。若测到日志写入导致事件循环停顿，再采用有界日志队列与独立写入线程。配合磁盘占用阈值及大小轮转。慢客户端选择及时关闭并提示重连，而不是持续发送很久以前的弹幕；具体阈值由可接受延迟决定并测试，不能静默丢弃业务评论。

## Nginx、DNS 和证书落地要求

1. 由用户域名下建立单独 A 记录指向该实例；检查是否存在错误 AAAA。先验证 DNS，再申请证书，避免重复失败触发签发限制。
2. Nginx 对外监听 80/443；应用切到 `127.0.0.1:8765`，云安全组与 UFW 同步调整。SSH 继续只允许管理出口；Redis 保持本地。不要依靠 Nginx 配置但同时把应用端口留给公网绕过。
3. 只把 `/ws/` 代理给应用，正确传递 HTTP/1.1、Upgrade、Connection；关闭代理缓冲，设置足够长的 read/send timeout。应用传输心跳与客户端文本 ping/pong继续保留。健康和详细指标限制内部访问；未匹配路径明确拒绝。
4. HTTP-01 使用固定 ACME challenge 目录，其余 HTTP 跳 HTTPS。CA 验证需要实际能够访问该子域的 80；不能仅给当前管理 IP 开放 80。若业务不接受该方式，再采用 DNS-01 及最小权限 DNS 凭证。
5. 免费证书可采用 Let's Encrypt + Certbot。安装后检查实际 timer/调度和续期配置；做一次续期 dry-run；部署 hook 在 `nginx -t` 成功后 reload；验证证书链、域名、有效期以及真实 WSS 收包。仅看到证书文件不算 HTTPS/WSS 已完成。
6. 证书续期使用 reload，避免直接 restart。长连接可能使旧 Nginx worker 保留较久，需观察进程并区分证书更新与应用更新；不要为了清掉旧 worker 强制切断所有用户连接。

## 建议实施顺序与验收

| 阶段 | 交付 | 验收证据 |
| --- | --- | --- |
| 1 | 根因级去重、连接阶段计时、重连快速路径 | 实际 protobuf 回归；不同 ID 同文保留；历史重叠抑制；明确故障样本与恢复时间 |
| 2 | 容量边界、输入校验、短空闲复用、重要状态/队列指标 | 限额压力下已有客户端可用；房间释放无任务泄漏；标签契约保持 |
| 3 | 域名、Nginx、HTTPS/WSS、自动续期 | DNS/证书链/HTTP 跳转/真实 WSS；关闭公网 8765；续期 dry-run 与 reload 通过 |
| 4 | Redis 与无关 SDK 事件路径优化 | 有输入速率、端到端处理延迟、事件循环延迟、内存高水位的可复现基准 |
| 5 | 新 release、回退与长时稳定性验证 | 同一构建本地/服务器测试；完整回退；多个房间低/高负载和网络故障验证 |

建议把正常状态下“SDK 收到评论→前端成功写入”的服务内处理延迟作为核心指标，设定例如 p95 < 100 ms 的初始目标后再用实测调整。它不等于主播发言到观众可见的完整网络延迟。重连目标也应分成：客户端连接切换、已检测的上游异常、半开网络故障、外部签名限流四类；不能用一个数字掩盖不同失败模式。

现有测试较好地覆盖了业务字段类型、Redis WRONGTYPE/超时降级、单房间复用、慢客户端隔离、ACK/心跳、取消及清理。主要缺口是同代重复来源、总容量、长时间高非评论流量、Redis 慢响应下的控制反馈、黑洞检测、Nginx WSS 和证书续期。新的验收应补这些差异，而不是反复运行同一批短单元测试来推断长期稳定。

## 后续扩展边界

单进程可继续服务多房间、多订阅者；保持它作为清晰的房间所有者。只有实际容量验证达到单机瓶颈后，才拆为“按房间分片的采集进程 + 分发层”，并为房间所有权加租约/隔离令牌，避免多个采集器重复连接同一房间。

若业务以后要求断线期间评论不丢、进程重启后可恢复历史，则需定义持久消息流、保留时间、客户端消费游标和确认协议；目前纯 WebSocket 加内存队列无法提供该保证。它会涉及业务协议与存储语义，应作为独立需求，不应在本次兼容优化中悄悄引入。

## 本轮实现的二次复核

在主任务加入快速重连后，独立复核发现并按主任务授权修正了以下三个问题；本节描述后续实施结果，前文仍保留首次审查时的证据与建议。

- 缓存有效期原先在排队前判断，连接信号量或全局签名冷却可能让缓存过期后仍使用。现改为结束等待、立即调用 start 前检查缓存年龄；分别有信号量等待、签名冷却两个回归。
- 缓存房间的签名 400/404 或 WebSocket 200 拒绝原先被直接视为终止，无法重新解析主播当前房间。现只允许一次完整重新解析；如果完整路径仍拒绝，正常终止。401/403 账号错误继续终止，429 继续遵守全局冷却。
- 每次握手成功再立即掉线原先都能覆盖指数退避，造成反复快速重签。现只允许一次立即恢复；只有连接持续达到 `retry_reset_after` 才补回该资格。重复短连接仍可利用未过期房间 ID 减少解析请求，但必须等待指数退避。

新增 `tests/test_manager_architecture.py`。先证明 6 个用例失败、5 个通过；修复后三个 manager 测试文件共 37 个通过；随后补充完整回退仍失败时必须终止的 3 个用例，新文件最终 14 个全部通过。Ruff 通过。这里只证明本地状态机与错误策略，没有把这些结果当作新的真实直播网络时延证据。
