# 真实直播与部署验证结果

服务已部署到 `163.7.2.127`，两个公开 TikTok 直播间均收到真实弹幕，人工断开上游连接后能够自动恢复，进程异常退出后能被 systemd 自动拉起。当前是使用本机空 Redis、未配置旧签名密钥、限制访问来源的部署；尚未切换现有生产业务。

测试日期：2026-09-09，北京时间 15:38 起；具体起止时间保存在各统计文件中。以下结论来自新服务器实际运行和本机 SSH 隧道测试，没有发送评论、点赞、礼物或关注操作。

## 真实弹幕

| 场景 | 观察时长 | 每个客户端收到的弹幕 | 首条弹幕 | 结果 |
| --- | --- | --- | --- | --- |
| `@y277902` 首次短测，2 个客户端 | 65 秒 | 各 12 条 | 9.206 秒 | 连接成功，心跳正常 |
| `@y277902` 持续观察，2 个客户端 | 600 秒 | 各 24 条 | 9.159 秒 | 包含一次人工断线与主播正常下播 |
| 本机经 SSH 隧道订阅同一房间 | 90 秒 | 2 条后续新弹幕 | 25.841 秒 | 复用服务器既有采集，无前端断线 |
| `@shalphoke69` 第二房间，2 个客户端 | 120 秒 | 各 31 条 | 3.867 秒 | 后续新弹幕持续收到，无连接错误 |
| 启用签名 TLS 校验后的 `@shalphoke69` 复测 | 90 秒 | 各 24 条 | 10.144 秒 | 签名、连接与后续弹幕正常 |

首条弹幕时间从测试脚本启动计算，包含连接初始化和等待消息，且可能来自历史批次；它不是观众发送到业务接收的端到端延迟。各客户端弹幕条数包含上游重复源 ID，不能直接作为独立评论人数或唯一消息数。

第一房间在持续观察的第 427.062 秒推送结束状态 `3`，网页同时确认“直播已结束”。结束后客户端心跳继续正常，服务没有不断重新发起采集。因此，600 秒是完整观察窗口，不能表述成主播连续在线 10 分钟。

同一房间的两个客户端复用一个上游采集；本机第三个客户端短暂加入时也复用该采集。第二房间接入时，已下播房间的前端订阅尚未结束，聚合健康数据短暂显示 2 个房间、4 个订阅，其中仅 1 个房间在线。所有测试客户端退出后，房间数、订阅数和队列均归零。

## 故障恢复与资源

- **上游断线**：在第 179.285 秒，服务感知到人工关闭其外部 443 TCP 连接；第 180.276 秒开始重连，第 194.190 秒恢复 `LIVING`。从错误状态到恢复约 **14.905 秒**。两个前端连接保持，之后继续收到新弹幕。测试限定于弹幕进程自己的外部连接，没有修改防火墙，没有中断 SSH、Redis 或其他进程。
- **进程异常**：所有测试订阅退出后，对弹幕主进程执行一次 SIGKILL。systemd 在 **6.048 秒**后拉起新进程且健康接口恢复。PID 从 9554 变为 9940，`NRestarts` 从 0 变为 1；该次重启是主动故障测试产生的。
- **心跳**：本机经 SSH 隧道的文本 `ping` / `pong` 往返中位数 **187.950 毫秒**、最大值 **212.289 毫秒**，9 次均有响应。服务器本机的心跳中位数约 0.5—0.7 毫秒；两种测量不可混为公网弹幕延迟。
- **队列与 Redis**：持续观察和第二房间的每 30 秒健康采样中，待处理事件与待发送消息均为 0；Redis 失败、降级均为 0。首次短测的初始采样有 1 条待发送状态消息。离散采样不代表采样间隔内从未出现短暂排队。
- **内存**：持续观察采样到的服务 RSS 为 **112084—114136 KiB（约 109.5—111.5 MiB）**。短时间低负载样本不能证明长期无泄漏或高并发容量。

## 重复消息与业务兼容

持续观察时，重连重放抑制计数达到 20，即两个客户端合计抑制 20 次跨连接代次的历史重放。每个客户端仍观察到 7 次相同源 ID 的重复，第二个房间为各 6 次。这是弹幕源 ID 的统计，采样没有保留完整消息指纹，尚未进一步区分初始历史与后续帧中的具体重复来源。

复查更正：实测中的两次下播状态 `3` 不能归为上游重发。SDK 会为同一控制帧生成 `LiveEndEvent`（继承 `ControlEvent`）和原始 `ControlEvent`；新适配层使用 `isinstance` 同时处理了二者，旧业务按事件类型名称订阅则只收到原始事件。暂停、恢复和 SUSPENDED 同样受影响。

适配层已修正为只处理原始 `ControlEvent`，状态值和正常控制消息顺序保持原样。新增 3 项回归测试通过真实 SDK 解析路径同时对照旧订阅行为：修复前全部失败，修复后完整 62 项通过。原始统计文件保留修复前结果，不能作为本次控制状态修复后的实测证据。部署状态与后续验证另见 [控制事件修复记录](control-event-fix.md)。

同一连接代次内按原业务语义转发，跨代次按配置抑制历史重放。当前不能承诺“无重复”或“端到端恰好一次”。测试没有与 TikTok 的完整原始消息清单逐条核对，也没有测量丢失率；网络中断期间可能有无法重放的消息。

JSON 字段、字符串 ID、文本状态与原 WebSocket 路径保留。返回标签字段来自新建本机 Redis 的查询逻辑；没有验证原生产订单标签和黑名单数据。

## 部署环境检查

- Ubuntu 24.04 / Python 3.12 上，**59 项回归测试全部通过，无跳过**；包含真实临时 Redis 和本地 WebSocket 集成，首次耗时 1.52 秒。签名 TLS 修正后，本机与服务器分别再次通过 59 项，服务器耗时 1.67 秒。测试输出只有 2 条上游弃用警告。
- 锁定运行依赖的 `pip check` 通过。默认云镜像源缺少锁定版本，改用官方 PyPI 后安装成功。
- systemd 服务由普通账号 `tiktoklive` 运行；开机启动、日志轮转、受限环境文件和系统目录只读保护已配置。
- SSH 使用密钥认证，已禁止密码认证；提供的 PEM 权限由 0644 收紧为 0600，密钥内容未修改。
- 签名 HTTP 客户端已从旧的 `verify=False` 改为 `verify=True`。启用校验后完成了上述 90 秒真实直播复测；部署文件 SHA-256 为 `4e693f3b622bc815c6afee7bb8f6bcb81ca6fe356cd43d54ed6f08aae8588923`，与本地文件一致。应用这处修正时进行了一次正常服务重启。
- Redis 监听回环地址；安全组与 UFW 均限制 22 和 8765 的来源。完整配置见 [部署记录](README.md)。

## 尚未完成的正式接入条件

1. **业务调用方网络**：本机直接请求公网 8765 出现 `Empty reply from server`，因此没有把公网直连标记为通过；SSH 隧道已实测通过。管理网络存在出口变化，正式客户端的固定出口 IP 或反向代理来源需要加入云安全组和 UFW。
2. **域名与 WSS**：当前未提供域名，尚未配置 HTTPS/WSS。外部浏览器正式接入还需要落实传输与访问方案。
3. **业务 Redis**：新建本机 Redis 不是原生产数据。正式使用订单标签与黑名单前需配置实际 Redis 地址及已授权凭据。
4. **签名账号**：自动审批曾阻止上传现有 `EULERSTREAM_API_KEY`，因此没有迁移该密钥；本次在未配置密钥的模式下实测成功。未验证该模式的正式配额、并发限制或长期可用性。

当前结果支持“这台服务器能连接真实 TikTok 直播、接收后续弹幕，并在本次故障场景下恢复”。没有进行 24 小时持续测试、高并发真实房间测试、生产前端验收或精确丢失率验证。
