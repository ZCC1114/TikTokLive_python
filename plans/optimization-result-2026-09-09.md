# TikTok 弹幕服务：本轮结果与整体优化方案

日期：2026-09-09。**新域名 `live.quick-pick.net` 已完成 DNS、免费 HTTPS/WSS 和自动续期验收，8765 已收回为回环入口**，见 [域名与本轮公网测试结果](../deploy/domain-https-2026-09-09.md)。两轮公网测试因上游拒绝/超时及签名冷却分别等约 70 秒和 65 秒才进入 LIVING；必须与下文 2.13/3.39 秒明确故障恢复样本分开判断。**正式签名配额及稳定性仍未解决，不能把受控恢复快解释为所有连接都快。**

业务目标保持国际版 TikTok、现有 `/ws/{live_id}`、文本 ping/pong、状态值、弹幕 JSON 字段及 Redis 标签规则。本轮已实施代码修复并发布到 `163.7.2.127`。

## 已确认的问题和修复

### 1. 弹幕重复来自两批历史重叠，服务去重范围不完整

真实直播 `@shalphoke69` 中，每次签名接口返回 6 条历史弹幕，进入 WebSocket 后又收到同样 6 条。源 ID 相同，protobuf payload 摘要也相同。三次上游连接均观察到这类重叠；没有观察到这段样本中独立的运行期 WS 重投或同 ID 内容变化。

此前服务仅在上游连接代次不同的情况下去重。因此同一次连接内的“签名历史→WebSocket 历史”都被转发，业务转换又为每次处理生成新的 `msgId`，前端无法依靠这个业务 UUID 自动认出同一源消息。

本轮按每个订阅者的 `(dyRoomId, dyMsgId)` 去重，同时覆盖同代和跨代；不改变业务字段和 UUID 语义。相同文本但不同源 ID 的发言继续发送，新订阅者有独立记录，ID 无效的消息继续保留。去重窗口默认最多 4096 条、300 秒；不是持久化或跨前端断线的恰好一次保证。

源码：`live_service/delivery.py`；来源计数：`TikTokLive/client/diagnostics.py`；真实协议解析回归：`tests/test_dedup.py`。诊断只导出计数，不保存弹幕正文、观众身份、Cookie 或签名 URL。

### 2. 重连改为有回退的快速路径

原路径每次重新解析主播房间、检查开播、请求签名、建立 WS；服务超时只覆盖创建 WS 任务之前的部分，未覆盖握手。签名内部与服务外部还各有重试，耗时不透明。

本轮措施：

- 短断线的下一轮复用刚确认在线的房间 ID，跳过解析和开播检查，仍请求全新签名。
- 缓存最长 60 秒，在连接排队和全局签名冷却结束后再检查有效期。
- 缓存房间被拒绝时，完整重新解析一次；401/403 账号拒绝和 429 限流遵守原错误策略。
- 首次快速恢复最多等待 0.2 秒随机抖动；反复短连接恢复后又断开时仍指数退避，稳定 30 秒才补回快速重试资格。
- 完整连接预算 20 秒、快速路径 10 秒、单次签名 8 秒；覆盖 WS 握手及入房发送，关闭签名内层重试，由一个监督器统一恢复。
- WS open timeout 5 秒、close timeout 1 秒；心跳发送已失败时立即终止坏连接，取消和超时释放读任务及 transport。
- TCP 探测改为服务专用配置：空闲 5 秒、间隔 2 秒、3 次，Linux user timeout 10 秒。没有用“几秒无弹幕”错误判断安静房间掉线。
- 内部健康数据增加解析、开播检查、签名、握手、总连接与恢复耗时。

这些超时是失败预算，不是所有网络环境下的成功延迟保证。签名服务不可用、限流、主播下播应分别处理。

### 3. 解析效率、容量与发布

服务不再为没有监听者的原始响应反复做 protobuf→字典→protobuf 复制，SDK 默认公开事件及显式 raw 监听仍兼容。本机 2000 条最小 Comment、三轮中位数的解析微基准从 4.6061 秒降至 1.1255 秒；只代表此解析环节，不能外推为网络速度或容量。

新增默认上限：50 个房间、1000 个订阅者、单房间 200 个订阅者；超限拒绝新连接，保留已有连接。保留一房间一个采集器、一个有界消费队列、每订阅者一个发送器和慢客户端隔离。上限是保护参数，尚不是这台 2 核 4 GiB 机器的实测容量承诺。

新版本安装在 `/opt/tiktoklive/releases/20260909-02`，独立虚拟环境；已切换 `current` 并重启正式服务。之前 `20260909-01` 完整保留，支持整版回退。部署未迁移实际业务 Redis 数据，也没有上传旧签名账号密钥。旧 Redis 配置文件没有重新从工作区上传，继续使用服务器已配置的本地 Redis。

## Nginx、域名及免费 HTTPS 当前进度

已完成：TrafficRoute DNS 下新建 `live.quick-pick.net` A→`163.7.2.127`，默认线路、TTL 600；Nginx/Certbot、TCP 80/443、正式 Let's Encrypt 免费证书与加密入口。当前证书到期时间为 2026-12-08 08:46:41 UTC。`certbot.timer` enabled/active，指定证书续期 dry-run、实际 deploy hook 回执及之后 TLS 复查全部通过。

公网 HTTPS `/healthz` 返回 200，HTTP 业务和 `/ws/` 路径返回 308，公网 `/readyz` 返回预期 403。公网 WSS 90 秒两个客户端各收到 9 条弹幕、0 重复，连接保持并响应 ping/pong；但首次上游可用约 70 秒，日志先出现 `InvalidStatusCode`，随后 `SignatureRateLimitError` 要求等待 53 秒。该证据说明域名与加密代理可用，同时也暴露签名限流仍会显著影响首次连接体验。探针健康采样的 `JSONDecodeError` 源于预期 403 页面，不能误报为服务故障。原始数据见 [probe-public-wss.json](../deploy/reports/probe-public-wss.json)。

已实际执行并通过验收的 [`deploy/configure_nginx.py`](../deploy/configure_nginx.py) 执行：

1. 校验域名与解析，仅接受该服务器 IPv4，避免错误 A/AAAA 导致间歇失败。
2. 为该子域设置 Nginx，使用 Let's Encrypt 免费证书和 HTTP-01 验证。
3. `/ws/` 保留路径并转发 Upgrade/Connection，禁用代理缓冲，read timeout 3600 秒，增加握手频率和连接数限制；详细 readyz 不对公网开放。
4. 检查实际证书信任链、域名和 HTTPS 应用健康；证书更新时先 `nginx -t` 再 reload。
5. 运行 `certbot renew --dry-run --run-deploy-hooks` 验证自动续期链路。

云安全组及 UFW 的 8765 规则均已移除，`ss` 确认应用仅监听 `127.0.0.1:8765`，systemd active，修改后公网 HTTPS 健康 200。75 秒 WSS 复验先签名 8 秒超时、再遇约 51 秒冷却，第 65.336 秒 LIVING，收到 6 条首批弹幕且无重复；最后约 10 秒无新评论，不能当作后续实时评论的再验证。SSH 继续保留管理出口白名单，Redis 只在本机。证据见 [最终状态](../deploy/reports/domain-https-state.json) 和 [收口后 WSS 报告](../deploy/reports/probe-public-wss-loopback.json)。本轮只针对 Nginx/证书执行的 29 项测试在本地与服务器均通过；之前完整功能回归 116 项，不宣称本轮执行了完整 128 项回归。

实现依据：[Nginx WebSocket 官方说明](https://nginx.org/en/docs/http/websocket.html)、[Certbot 官方说明](https://certbot.eff.org/instructions?os=snap&ws=nginx)。本轮使用正式受信任证书，并验证续期及重载链路。

## 整体架构方案及后续优先级

建议保留目前已经验证的房间复用结构。它的主要边界现在在外部签名、标签查询和公网接入；整体推倒重写不会自动缩短这些等待，而且会扩大协议兼容风险。

```text
客户端 WSS
    ↓
Nginx：TLS、握手限制、连接限制、代理心跳
    ↓
连接管理：容量、房间所有权、状态机、取消和重连
    ↓
每房间一个 TikTok SDK：新签名、入房、ACK、心跳、来源诊断
    ↓
有界有序队列 → Redis 实时标签 → 每订阅者源 ID 去重 → 单发送器
```

| 顺序 | 优化内容 | 验收方式与约束 |
| --- | --- | --- |
| P0，完成业务接入 | DNS/HTTPS/WSS/续期及 8765 收口已验收；仍需确认正式签名配额、调用端和实际 Redis | 处理已经出现的约 65/70 秒签名等待；标签与旧服务一致；保持现有业务消息 |
| P1，长期质量 | 记录队列高水位/最老年龄、Redis p95、SDK 收包到前端写入耗时、累计失败原因 | 以正常负载服务内处理 p95 <100ms 为待验证目标；至少覆盖 24 小时和多个活跃房间，区别安静与断线 |
| P1，故障发现 | 测试真实丢包、半开连接、DNS 失败、签名 429、Redis 变慢 | 分别测故障发现与恢复；不能靠无评论强制断线。已发现异常的恢复初始目标 2–4 秒，受签名服务约束 |
| P1，签名等待 | 加 TCP/TLS/响应头等待分解；确认正式签名服务配额与区域能力 | 当前主要等待在签名；先有测量再决定长连接池或签名服务方案，不猜未提供的地域参数 |
| P2，前端瞬断体验 | 评估将 LIVE_IDLE_GRACE 从 0 配为 2–3 秒 | 页面刷新/客户端短断线复用采集器，超期完全释放；这是可配置优化，当前默认保持 0 |
| P2，高负载标签查询 | 有界批量 Redis pipeline 或有限并发后按序输出；跳过全体订阅者已见重复的多余查询 | 维持标签实时性、旧错误语义和评论/控制状态顺序；以慢 Redis + 高消息速率压测决定，不引入随意标签缓存 |
| P2，日志和发布 | 异常日志限频/脱敏、磁盘体积上限；统一环境注入、构建哈希与回退检查 | 不记录原始损坏帧内容；不依赖人工打包差异；正式旧配置迁移需明确配置来源 |
| P3，达到单机瓶颈再拆分 | 按房间分片采集 + 分发层 + 房间租约/隔离令牌 | 防止多 worker 各采一次同房间。没有容量证据前不直接加 worker 或引入 Kafka |

若未来要求前端重连/进程重启后也绝不重复、断线期间不丢，需新增持久消息流、消费游标和客户端确认。这会涉及接入协议，不应在“业务流程不变”的本轮里偷偷改变。目前修复的是已接收源消息的重复投递和连接恢复，不把内存去重宣传成端到端不丢不重。

所有模块的独立审查、逐项代码证据和更多边界见 [架构审查](architecture-review-2026-09-09.md)。其中前半部分是修复前的问题快照，已实施项以本文为准。
